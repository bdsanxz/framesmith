## 1. The command line

```
framesmith render <path> [--output <file>] [--backend <word>] [--quality <word>] [--encoder <word>] [--codec <word>] [--workers <value>] [--marks]
```

- **One argument, the path of the project**, in the three forms `project-location.md` gives (a folder, a `framesmith.yaml`, a composition file), and any of the options below, before or after it, in any order.
- **The options.** Each sets the one setting of the project file it names, for this run only (section 1.1). An option is written as `--quality high` or as `--quality=high`; the word after an option that takes a value is its value, even when it begins with `-`.

| Option | The setting it replaces | Values taken |
|---|---|---|
| `--output <file>` | `render.output` | A path that is not empty |
| `--backend <word>` | `render.backend` | `auto`, `cpu`, `gpu` |
| `--quality <word>` | `render.quality` | `draft`, `standard`, `high` |
| `--encoder <word>` | `render.encoder` | `hardware`, `software` |
| `--codec <word>` | `render.codec` | `h264`, `hevc` |
| `--workers <value>` | `render.workers` | `auto`, or a whole number from 1 to 16 written in digits |

  `--marks` takes no value and sets no setting: the summary then ends with the mark of every frame drawn (section 7.1). It is written `--marks` alone; `--marks=yes` and `--marks` given twice are options not taken.

  The values are those of the project file's keys (`project-file.md` section 3), letter for letter. `--backend` chooses the renderer, by section 1.2: `cpu` draws on the processor, `gpu` draws on the graphics card (`card-renderer.md`), and `auto`, the default, draws on the card when one is there and on the processor when none is. What `--codec` does to the film is stated in section 5.3; what `--encoder`, `--quality` and `--workers` do is stated by their own tickets (T085, T096); a value this version does not apply is refused before the first frame (section 3). `--json`, `--strict`, `--debug` and settings by environment variable are not taken in this version. `render.audio-bitrate` has no option in this version (`ROADMAP.md` line 1.48 lists none): it is set in the project file.
- **A command line that cannot be read** (`FS-0017`): no path, or more than one path. Its remedy is about the path of the project.
- **An option that is not taken** (`FS-0037`, of the kind invalid): an option that is not in the table, an option with no value after it, an option given twice, and a value outside the values of its option. Its remedy is ``Give one of the options the message lists, with one of the values it names, or leave the option out.``, so that the author is sent to the option, not to the path. The message names what was written and the options or values taken:
  - ``--colour` is not an option of `render`; the options are: --output, --backend, --quality, --encoder, --codec, --workers, --marks``;
  - ``--quality` must be one of draft, standard, high, not ultra``;
  - ``--workers` must be auto or a whole number from 1 to 16, not 17``;
  - ``--output` must be a path that is not empty``;
  - ``--quality` needs a value: one of draft, standard, high``;
  - ``--quality` is given twice; give it once``;
  - ``--marks` takes no value, and is written alone``.

  Both are told on standard error as `check` tells a command line it cannot read (`framesmith: ` and the statement of the code), followed by the usage line of `render`, which names every option and its values:

  ```
  usage: framesmith render <path> [--output <path>] [--backend auto|cpu|gpu] [--quality draft|standard|high] [--encoder hardware|software] [--codec h264|hevc] [--workers auto|1-16] [--marks]
  ```

  then nothing is printed on standard output, the project is not opened, nothing is written, and the exit code is 1 (decision A19: a value outside its list is invalid and ends with 1). A command line with no command, or with a word that is not a command, is told with both usage lines, `usage: framesmith check <path>` and the usage line of `render` above, in that order.

### 1.1 Which value is used

Every setting is taken by one rule: **an option on the command line wins over the project file, and the project file wins over the default** (`project-file.md` section 1). An option replaces only the setting it names; every other setting keeps the value of the project file, or its default. The setting in use is what the rest of this spec means by the setting: what is refused (section 3), the place of the finished file (section 6), the sound's bit rate (section 5.2) and the summary (section 7). `framesmith.yaml` is read and never written: an option changes the run, not the file.

### 1.2 Which renderer draws

The renderer is chosen once, from `render.backend` (or `--backend`) as section 1.1 gives its value, before the film is opened and before the first frame. The choice is made in one place of the program, and nothing else chooses.

- **`cpu`** draws on the processor (`draw-cpu`). The card is not started.
- **`gpu`** draws on the graphics card (`card-renderer.md`). When this machine has no card that frx7 can draw with, or the card could not be started, `render` refuses the film: the report of `FS-0038` (section 7) and no file. A `gpu` is never drawn on the processor: Framesmith does not fall back from `gpu` to `cpu`.
- **`auto`**, the default, starts the card first. When the card starts, `auto` draws on it. When it does not start, `auto` draws on the processor, and the summary says so (section 7). So `auto` never refuses a film for want of a card.

The renderer that draws is named in the summary (section 7) and in the run log (`run-log.md` section 4), so that a choice Framesmith made is always shown. Choosing among several cards is not in this version.

## 2. What is read, and what is written when it is not drawn

- The project is opened by `Project::open`, the one reading `check` uses. When it has any report, or there is no project, the command prints exactly what `check` prints for it (the reports and the closing line, or the `No project` line), writes no file and makes no folder, and ends as `check` ends: with 1, or with 2 when every report is of the kind unsupported (decision P2).
- A project that opens is then looked at for what this version draws and applies (section 3). When anything in it is refused, every refusal is printed as a report, in the order of the files (the command line first, then the project file) and of their lines, then the closing line `Invalid: the project is not valid (composition.xml)` or, when every report is of the kind unsupported, `Unsupported: the project uses what this version does not support (composition.xml)`, with the files that have a report in the brackets. Nothing is written, no folder is made, and the exit code is 1 or 2 by the same rule. `check` lists the forms that it judges (`check-command.md`, sections 3b and 3c, and the text forms of `text.md`, sections 1 and 8). The other refusals are listed by `render` and not by `check` in this version: the table of what is not supported (`notation.md` section 14) is built later and `check` lists from it, so a project that `check` calls ready can be refused by `render` until then.
- Only after both, the first frame is drawn. A failure after that point (section 5) leaves no file at the place of the finished file. The renderer is chosen before the first frame, and the card of `--backend gpu` or of `--backend auto` is started then (section 1.2): a `gpu` on a machine with no card that frx7 can draw with (`card-renderer.md` section 2) is refused with the report of `FS-0038` and the closing line of section 7, and no file is written. With `auto` the same machine draws on the processor, and the film is written.

## 4. The picture

A frame is a picture of `width` by `height` pixels, each pixel four bytes in the order red, green, blue, alpha, rows from the top, no padding between rows. It is drawn as follows, and the result is the correct picture of this version:

1. Every pixel is the root's background (black, `#000000`, when it is not written) with alpha 255.
2. The boxes are drawn in document order, a parent before its children, each over what is there: a box with a `background` replaces every pixel with `left <= x < left + width` and `top <= y < top + height`, the rectangle of section 4.1, that lies inside the frame by the box's colour, alpha 255. A box written later covers one written earlier where they overlap, and a box inside a box is drawn over the box that holds it (`notation.md` section 3, drawing order; Q2). A box with no `background`, or with a size of 0, changes nothing. A box is drawn in the frames of its window (section 4.2) and in no other frame; in a frame outside its window it is not drawn at all, and its children with it.

There is no smoothing: a box's edge is a whole pixel boundary, since every edge is worked out to whole pixels (section 4.1). An element that is moved by other than whole pixels, scaled, turned or slanted is smoothed by its coverage (section 4.5).

**A frame is a pure function of the composition and the frame's number.** A box appears and disappears only with its window (section 4.2), and an element moves only by its tweens, whose values are worked out for the frame's own time (section 4.5). The picture of a frame never depends on the frames drawn before it, on the order they are asked for, on the clock, or on the number of workers. A frame number at or past the frame count is not a frame; it is refused when asked for.

The renderer on the card (`--backend gpu`, and `--backend auto` when a card is there: section 1.2) draws the same display list, and its picture must agree with this one within the tolerance of `card-renderer.md` section 4. The picture of the processor is the correct one; the card's is checked against it on every frame of the fixture, and is not checked in.

### 4.1 The place and the size of a box

The place and the size of every `<box>` are worked out once, before the first frame, and are the same in every frame (`PLAN.md`, section 3). The rules are those of `notation.md` section 7.1, with Q1 (`bottom` and `right` with a size), Q2 (a box counted from its parent's outer edges, drawn in document order) and N10 (`margin`, which moves an absolutely placed box in from the edges it is placed by, B37 and B41: rule 8). The parent of a box in the root is the frame. The parent of a box inside a box is that box, and its rectangle is the one worked out here: a parent is worked out before its children.

Each axis is worked out on its own: across, from `left`, `right` and `width`, with the parent's width; down, from `top`, `bottom` and `height`, with the parent's height. Let L be the parent's width or height in pixels. An amount is a number of pixels, as written, or a percentage p of L, which is p times L divided by 100 pixels, exactly and not rounded.

1. **Size.** A written `width` or `height` is its amount. Otherwise, with both edges of the axis written (`left` and `right`, or `top` and `bottom`), the size is L less the two distances. Otherwise it is L: a box with no size is as large as its parent, and a `left` or a `top` alone does not reduce it. A size that comes out below 0 from the two distances is 0. A size written below 0 is reported (N6).
2. **Start.** A written `left` or `top` is the distance of the near edge from the parent's near edge. With no near edge and a far edge written (`right` or `bottom`), the far edge lies that distance from the parent's far edge, and the near edge is L less that distance less the size. With neither, the near edge is the parent's near edge. A written near edge is used even when a far edge is written too, and a written size is kept even when a far edge is written (Q1).
3. **Whole pixels.** Exactly, the near edge a is the parent's near edge plus the start, and the far edge b is a plus the size. Each of a and b is rounded to a whole pixel, a half up: the whole number nearest to it, and a value of exactly half a pixel goes to the larger whole number. A written amount is exact: a pixel amount and a percentage are the decimal as written, with every digit it is written with (`1.4%` is 14 tenths of a per cent), so `1.4%` of 2750 is exactly 38.5. A percentage p of L is worked out with no float in it, and the sum of the near edge and the size is exact, so the rounding is done on the exact sum. A value a float computes, such as a value of motion (`motion.md`), is a float and is rounded as it is. The box covers the pixels from round(a) up to round(b) less one, so its size is round(b) less round(a), and two boxes that meet share one edge. A box of size 0 covers no pixel. Example: in a frame 96 pixels wide, `left="10%" width="50%"` gives a = 9.6 and b = 57.6, which round to 10 and 58, so the box covers the columns 10 to 57, 48 pixels; in a parent 99 pixels wide, `width="50%"` gives 49.5, which rounds to 50.
4. **Nesting.** A box inside a box is placed in the same way, from its parent's rectangle as rule 3 worked it out: L is the parent's width or height in whole pixels, and its near edge is the parent's whole-pixel edge. A box with `left="10"` inside a parent at `left="20"` lies at 30. Moving the parent moves the box with it. A child of a box with `flex-direction` is placed by the rows and columns of section 4.3 instead: its rectangle is worked out with its siblings, not by its own edges alone.
5. **Zero and negative.** A `width` or `height` of 0, or of `0%`, draws nothing of the box, and its children are still placed and drawn (N6). A `width` or `height` below 0 is reported with `FS-0034` (section 3) and the box is not drawn.
6. **Limit.** When a rounded edge, or the size, lies beyond 1000000 pixels, or an amount cannot be worked out as a finite number, the box is not placed and is reported with `FS-0035` (section 3). A sum, or a product, of two written amounts whose digits would have to be shifted more than 100000 places to line up is not worked out either, and the box is reported the same way: the bound keeps the work of one written value finite, since an exponent of 1e9 would otherwise ask for a billion zeros. Every other digit a written amount has is kept.
7. **Widest width.** `max-width` (a number above 0, in pixels) caps the width of a box whose width does not come from its own written `width`: the size of rule 1 is made no larger than it, whether the size comes from the parent, from two edges, or from the items of a row, a column or a set of columns (section 4.3, rule 13; section 4.4). The start of rule 2 is worked out from the capped size. A box with a `width` of its own ignores `max-width`. A text is wrapped and sized as `text.md` section 5.3 says.
8. **Margin of an absolutely placed item.** On an absolutely placed `<box>`, `<text>` or `<composition src>` (one with `position="absolute"` in a row, a column or a set of columns, and every one in a plain box, whether or not it writes `position`: `notation.md` section 7.1, decision B41), the `margin` (the sides of `notation.md` section 4, in pixels) moves the item in from each edge that places it, as CSS does (N10, decisions B37 and B41; CSS 2.1, sections 10.3.7 and 10.6.4, read for their meaning). On each axis, with m₁ the margin on the near side and m₂ on the far side:
   - with a near edge written (`left` or `top`), the start of rule 2 is that distance plus m₁;
   - with no near edge and a far edge written (`right` or `bottom`), the far edge lies that distance plus m₂ from the parent's far edge, and the near edge is L less that distance less m₂ less the size;
   - with both edges written and no size, the size of rule 1 is L less the two distances less m₁ less m₂, 0 when that is below 0, and the start is the near distance plus m₁;
   - with neither edge, the item lies at its static position moved in by m₁: in a plain box the start of rule 2 is m₁; in a row, a column or a set of columns it is the start the container would give the item, at its size of rule 1, if it were the container's only item (section 4.3, rule 6; section 4.4, rule 7), which counts m₁ as the margin of any item does. m₂ moves nothing.

   The sums of the written amounts and the margins are exact, as rule 3 says, and the edges a and b are then rounded once, by rule 3. Example: in a frame 96 by 54, `position="absolute" left="50" top="10" width="20" height="20" margin="30"` gives a = 80 and b = 100 across, so the box covers the columns 80 to 95 inside the frame, and a = 40 and b = 60 down, so it covers the rows 40 to 53. The same box with no `position` in the frame is placed the same way. A box with `width="20" height="10" margin="18 0 0 14"` and no edge, in a plain box at (0, 0), covers the columns 14 to 33 and the rows 18 to 27.

**Settled by.** T041 of Sprint 1 (brigade order t041): the whole-pixel rule of 3, the size of 0 for a size below 0 that comes from two distances (1) and the limit of 6 are not in `notation.md`. Rule 8 is settled by decisions B37 and B41 (2026-10-26). B63 (`DECISIONS.md`, 2026-10-27) confirmed the rules 1 and 3 as written.

### 4.2 The window of a box

A `<box>` written with `start` and `duration` (both, or neither: `notation.md` section 5.2) is drawn only in the frames of its window. A `<box>` written with neither is drawn in every frame of its parent's life. The window is worked out once, before the first frame, by the frame-grid rule of `frame-time.md`:

1. **Origin.** A `start` counts from the start of the nearest clip around the element: the nearest parent that has both `start` and `duration`. With no clip around it, it counts from the start of the composition, which is time 0. An element between the clip and the box that has neither `start` nor `duration` passes the origin on unchanged. The start of a clip is its origin plus its written `start`, added exactly; the origin of everything inside that clip is that start.
2. **Window.** For a box with `start` and `duration`, let `s` be its start (its origin plus its `start`) and `e` be `s` plus its `duration`, both exact. Its window is the frames `i` with `F(s) <= i < F(e)`, where `F` is the frame-grid rule. A `duration` of 0 gives an empty window: the box is not drawn.
3. **Within the parent.** A box's window is its own window cut to its parent's: a frame is in the window only when it is in both. A box with neither `start` nor `duration` has its parent's window. The root's window is every frame of the composition. So a child is never drawn outside its parent's window, whatever its own window says.
4. **Place.** A window changes no place: the place of section 4.1 is the same in every frame, and a box outside its window keeps its place.

At 30 frames a second, a clip from 1 s for 2 s is drawn on frames 30 to 89. A box inside it with `start="0.5"` begins at 1.5 s and first shows on frame 45. A box inside it with neither `start` nor `duration` shows on frames 30 to 89 as well. A box with `start="0.33333"` and one with `start="0.33334"` both first show on frame 10; one with `start="0.34"` first shows on frame 11.

**Settled by.** T042 of Sprint 1 (brigade order t042): the origin of rule 1 (the nearest clip, passed through an element that has neither), the cut of rule 3 to the parent's window, and the empty window of a duration of 0 are not in `notation.md` in these words; section 5.2 names only the parent clip. They are a draft for the owner to confirm; the report of the order says so.

### 4.3 Rows and columns

A `<box>` with `flex-direction` lays out its children as a row (`row`) or a column (`column`). Its children are the `<box>` elements it holds, in document order. A `<box>` without `flex-direction` places its children by their edges (section 4.1). The values of `justify-content`, `align-items`, `align-self`, `gap` and `padding` are judged on every `<box>`, and they have an effect only on a box with `flex-direction` (rule 10).

Along the **main axis** of a row, which is across, the width counts; of a column, down, the height. The **cross axis** is the other one. Each item's **outer size** is its size on the main axis plus its `margin` on the two sides of that axis. The **content box** of a container is its rectangle less its `padding`.

1. **The container's size.** A row or column is placed by section 4.1 like any box, with one difference: an axis on which it has no size of its own (no written size, and not both edges) is as large as its items. On the main axis it is the sum of the items' outer sizes, the gaps between them and the padding on that axis. On the cross axis it is the largest of the items' outer sizes across, and the padding on that axis; an item that stretches (rule 7) and writes no size across counts with its margins only, since its size across is the container's, not its own. The exception is an item that is itself a row or column with no size of its own across: it counts the size its own items, gaps and padding give it across (from the inside out, as rule 3 says), with its margins, and it then stretches to the content box across as before (rule 7). A plain `<box>` that stretches counts its margins only, since its children give it no size. With no items it is the padding alone. A container with a size of its own keeps it.
2. **Items.** The items are the `<box>` children of the container, in document order, each one that is not `position="absolute"` (rule 6). An item takes no notice of its own `left`, `top`, `right` and `bottom`. There is no wrapping and no shrinking: an item keeps its size, and the items are never cut or moved to a new line.
3. **Size of an item.** On the main axis an item is its written `width` (row) or `height` (column). A percentage is of the container's size on that axis, when the container has a size of its own there (section 7.1); otherwise a percentage counts as 0. An item that writes no size on an axis is 0 there, unless it is a row or column with no size of its own on that axis: it is then as large there as its own items, gaps and padding make it (rule 1), worked out from the inside out to any depth, and is placed and aligned in its parent like any other item. A plain `<box>` that writes no size is 0 there, whatever its children, since they are placed by their edges and give it no size. On the cross axis a percentage is resolved as on the main axis, and an item that writes no size there is 0 unless rule 7 stretches it.
4. **Gap.** `gap` (default `0`) is the space between two neighbouring items: none before the first and none after the last. A gap of 0 leaves the items touching, and draws no gap. A gap below 0 is reported (`FS-0034`, section 3) and nothing is drawn. Absolute items take no room and are not counted in the gaps (rule 6).
5. **Along the direction.** `justify-content` (default `flex-start`) places the group of items, from the first item's outer edge to the last item's, with the gaps between them. `flex-start` puts the group at the start edge of the content box, `flex-end` at its end edge, and `center` leaves the same room on both sides. `space-between` puts the first item at the start edge of the content box, the last at its end edge, and shares the room left over equally between each two neighbours, on top of `gap`; with one item, or with no room left over, it is the same as `flex-start`. A group larger than the content box is placed as the value says and runs over the edges, as an absolute item may. The written sizes, gaps and margins of the group are summed exactly. The room that `space-between` and `center` divide, and the share of it an item takes, are floats, and rule 9 rounds the edges that come of them.
6. **Absolute items.** An item with `position="absolute"` takes no room, is not counted in the gaps, and does not move the others: the other items close up. It is placed by its own `left`, `top`, `right`, `bottom`, `width` and `height` as section 4.1 says, counted from the container's outer edges and not inside its padding (Q2), and it is drawn in document order with its siblings (Q2). Its `margin` moves it in from each edge it is placed by, as section 4.1, rule 8 says (N10, B37). On an axis where it writes neither edge it lies at its static position: where the row or column would place it, at its own size, if it were its only item (by `padding`, `justify-content` along and `align-self` or `align-items` across, its margins counted as any item's), as CSS places an absolutely positioned child of a flex container (N10, B41).
7. **Across.** `align-items` (default `stretch`), or `align-self` on one item, places each item across the content box, with its margins on the two sides across. `flex-start` puts the item at the start edge, `flex-end` at the end edge and `center` in the middle. `stretch` sizes an item that writes no size across to the content box across, less its margins. That holds whether the container has a size of its own across or takes one from its items (rule 1): then the items' sizes are found first, and the stretching items fill the size they give. A row or column with no size of its own across counts, in its container's size across, the size its own items give it (rule 1), and stretches to the content box across like any other item that writes no size across; a plain `<box>` that stretches counts its margins only. An item that writes a size keeps it and is placed at the start edge.
   `baseline` (in a row only) sets each item that has it so that the baselines of their first lines lie on one line, and the highest of them touches the content box's top edge. The baseline of an item is that of its first line when it is a `<text>`; of a row, a column or a set of columns, that of its first item, counted from its top (rule 14 and section 4.4); of anything else, its bottom edge. Each item with `baseline` is placed so that its baseline lies at the common line; the margins are counted from its outer edges. A row with no height is as high as its items need when they stand so: the highest part above the line plus the lowest part below it, with the other items' outer sizes if they are taller. In a column, `baseline` is `flex-start`.
8. **Padding.** `padding` (default `0`) is one to four numbers, read as the sides of section 4: `4` for all four sides, `4 8` for the top and bottom and then the left and right, `4 8 2` for the top, then the sides, then the bottom, `4 8 2 6` for the top, right, bottom and left. The items are placed inside the content box, so a padding moves them in from the box's edge by its amount on each side written. A written `width` or `height` of a row or column includes its padding (B17, `DECISIONS.md`): `width="80" padding="8"` is 80 wide, with 64 for its items, as in CSS's `border-box`. The same holds for a written `width` or `height` of a set of columns (section 4.4). A padding below 0 is reported (`FS-0034`).
9. **Items' edges.** Each item's edges are worked out as section 4.1 rule 3 says: exactly, the item's edges on each axis are placed as above, then each is rounded a half up to a whole pixel, so that two neighbours with a gap of 0 meet on one pixel edge. The sums of written sizes, gaps and margins are exact; a share of divided room (rule 5, and the share of spare room of rule 12) is a float, and the edge that comes of it is rounded from that float.
10. **Values.** `flex-direction` is `row` or `column`. `justify-content` is `flex-start`, `center`, `flex-end` or `space-between`. `align-items` and `align-self` are `flex-start`, `center`, `flex-end`, `stretch` or `baseline`. A word that is not one of these is reported (`FS-0039`, section 3). A `<box>` with both `columns` and `flex-direction` is reported (`FS-0055`, section 4.4). On a `<box>` without `flex-direction`, `justify-content`, `align-items`, `align-self`, `gap` and `padding` are judged for their form and have no effect.
11. **Clips.** A child with `start` and `duration` takes its room in the row or column during the whole composition, and it is only not drawn outside its window (Q3, section 4.2). The place of an item is the same in every frame. A clip that is not yet shown keeps its place in the flow on the frame before its start and on the frame after it, and the children after it are placed as if it were shown: the place is the one of rule 11 in every frame. A clip that has ended keeps its place in the same way.
12. **Shares of the spare room.** `flex-grow` (default `0`) of an item with a value above 0 gives it a share of the spare room along the direction: the room that the content box leaves over once every item's outer size and the gaps are taken off. The share is the spare room times the item's value, divided by the sum of the values of all items, and is added to the item's size on the main axis. It is worked out only when the row or column has a size of its own on the main axis (the width of a row, the height of a column); with no spare room, or with no value above 0, no item grows. The share is worked out in floats, and the edges it gives are rounded as rule 9 says.
13. **Widest width of an item.** An item whose `width` does not come from its own written `width` (`max-width`, section 4.1, rule 7) is never wider than that: the size it takes on the main axis of a row, or across a column (the width), is made no larger, after its share of the spare room (rule 12) has been added. An item with a written `width` of its own ignores `max-width`.
14. **Texts in a row or column.** A `<text>` in a row or a column is an item of it, placed as a box is. Its size is that of its text (`text.md` section 8): a text with no `width` is as wide as its widest line, and one with no `height` is as high as its lines, and it is not stretched across: `stretch` leaves it at its own size and at the start edge of the content box. Its `margin`, `align-self`, `flex-grow` and `max-width` act as they do for a `<box>`. A `<text>` with `position="absolute"` is placed by its edges, as an absolute box is, and its `margin` moves it in from those edges (section 4.1, rule 8). One form of it is not drawn in this version: an absolute `<text>` with `left` and `right` and no `width`, which `framesmith check` reports and `framesmith render` refuses with FS-0035 on the line of the `<text>` (`text.md`, section 8).

The sources of these rules are `notation.md` sections 7.1 and 7.2, with N6 for the zero and the negative values, N10 for `margin`, and Q2 and Q3 for absolute items and clips. The proofs' reference of the same rules, `native-notation-reference.md` section 4.3 in the proofs' tree, was read for the behaviour only.

**Settled by.** Nothing in this section is a draft. The owner settled the padding of rule 8 on 2026-10-16 (B17, `DECISIONS.md`): the padding lies inside a written `width` or `height` of a row or column, as CSS's `border-box` does. The brigade lead settled the other rules that the sources do not state in these words, under the project rule that the notation takes CSS's names and meanings where CSS has them (`CLAUDE.md`, section 1): the container's size counting the items' margins (rule 1), a group larger than its container running over its edges (rule 5), an item that writes no size being 0 on an axis when it is a plain `<box>` (rule 3), and the stretch of rule 7, which fills the content box whether the size across is written or taken from the items. A row or column that is an item and has no size on an axis takes the size of its own items there (rules 1 and 3), from the inside out, as brigade order t043 (round 2) settled. Rules 5, 7, 8, 11 to 14 and section 4.4 state the forms of `notation.md` sections 7.1 and 7.2 (T047, brigade order t047, which took them from the proofs' record in `native-notation.md` section 13). The reading of `notation.md` section 7.2 that `stretch` leaves a `<text>` at its own size (rule 14) is a reading of the words "a `<text>` and a `<span>` fit their text" in section 7.1, and is for the owner to confirm; `flex-grow` has no effect in a set of columns, which has no direction, as CSS gives `flex-grow` no meaning on the items of a grid and the notation takes CSS's meanings where CSS has them (section 4.4, rule 6).

### 4.4 Sets of columns

A `<box>` with `columns` lays out its children in columns, row by row: the first child in the first column, the next in the second, and after the last column a new row begins. Its children are the `<box>`, `<text>` and `<composition src>` elements it holds, in document order, and the rules of section 4.3 for the padding, the margins, the gap, the placing of absolute children (rule 6) and the widths of the items apply to it as they are stated there. Sources: `notation.md` section 7.2, and the proofs' record of the same form (`native-notation.md` section 13).

1. **Widths.** `columns` is a list of column widths separated by spaces. A width is a number of pixels above 0 (`640`), or a share of what is left (`1fr`, `2fr`), above 0. The room that the content box leaves after the pixel columns and the gaps is divided among the share columns in proportion to their numbers.
2. **Size of the box.** A written `width` or `height` includes its padding (rule 8, `DECISIONS.md` B17): the content box is the size less the padding. With no written width the box is as wide as its pixel columns, the gaps between them and its padding, and each share column is as wide as its widest item, counting the item's own width (written, or the size its own items give it) with its margins. With no written height the box is as high as its rows, the gaps between them and its padding. A percentage of an item is of the box's content box on that axis, and is 0 where the box has no size of its own there.
3. **Rows.** The children fill the first row from left to right, then the next row. `gap` is the space between two columns and between two rows (none before the first or after the last). A row is as high as its tallest item, the item's margins included. When the box has a height and the rows need less, what is left over is shared equally among the rows.
4. **Items.** An item is as wide as its column, less its margins, unless it has a written `width` of its own; then it lies at the start edge of its column, at that width. Across its row it stands as `align-items` of the box says, or as its own `align-self` says: `stretch` makes it as high as its row when it writes no height, and `flex-start`, `center` and `flex-end` place it at the start, the middle or the end of the row, at its own height (or the height its own items give it). In a set of columns `baseline` is `flex-start`.
5. **Widest width.** `max-width` of an item caps its width as rule 13 of section 4.3 says, for an item that writes no `width` of its own.
6. **Shares of the spare room.** A set of columns has no direction, so `flex-grow` of its items has no effect in it. A set of columns lays its items out row by row in columns, as a CSS grid does, and CSS gives `flex-grow` no meaning on the items of a grid; the notation takes CSS's meanings where CSS has them (`CLAUDE.md`, section 1).
7. **Padding and absolute children.** The items are placed inside the content box, so the padding moves them in from the box's edges by the amounts written. A child with `position="absolute"` takes no room, is not counted in the gaps, and is placed by its edges as rule 6 of section 4.3 says. On an axis where it writes neither edge it lies at its static position: where the set would place it, at its own size, if it were its only item (in the first row and column, by the padding and `align-self` or `align-items`, its margins counted as any item's) (N10, B41).
8. **Baseline of the box.** The baseline of a set of columns is that of its first item, counted from the box's top (`text.md` section 8, and section 4.3, rule 7); with no item it is the bottom edge.
9. **Refusals.** A `<box>` with `columns` and `flex-direction` is reported with `FS-0055`, and the box is not drawn (section 3). A `columns` that is not a list of column widths is reported with `FS-0054`. A column width of 0 or below is reported with `FS-0053`. Each is reported on the line of the box's `columns` attribute, as the other forms are (section 3). An absolute `<text>` in a set of columns with `left` and `right` and no `width` is refused in the same way as one in a row or a column, on the line of the `<text>` (`text.md`, section 8).

### 4.5 Motion

Sources: `notation.md` sections 7.8 (`transform-origin`, `perspective`, `rotate-x`, `rotate-y`), 8.1, 8.2 and 8.5; `motion.md` (the value of a property at a time); the 2D affine maps of plane geometry, written out here by us. An element that moves is a `<box>` or a `<text>` (section 3).

1. **The value at a frame.** Frame `n` is at the exact time `n / fps`. The value of each of the nine properties of an element at that time (and of `count` and `typed`, which change a text's content, `text.md` section 7) is the one `motion.md` gives from the element's tweens and sets, in the order of their `at` and, for the same `at`, in the order they are written (`notation.md` sections 8.3 and 8.5), with the element's own value the attribute it writes (`x="20"`) or else the starting value of `notation.md` section 8.1. A tween's or a set's `at` is in the time of the element's parent: the origin of the parent's slot (section 4.2, rule 1) plus the written `at`, added exactly, which is the time the element's own `start` counts in. The values are worked out from the time alone; nothing is played.
2. **The origin.** `transform-origin` is two lengths `x y`, each a number of pixels or a percentage of the element's width (for `x`) or height (for `y`), from the top left corner of the element's rectangle in the frame (section 4.1; for a `<text>`, the rectangle of its paragraph, `text.md` section 8). It is `50% 50%` when not written. The origin `O` is that point in pixels of the frame, not rounded.
3. **The map.** The element's map takes a point `p` of its picture to `T(x, y) · T(O) · R · K · S · T(−O)`, the rightmost first: the point is taken relative to the origin, scaled by `scale × scale-x` across and `scale` down, slanted by `skew-y` (a point `d` pixels right of the origin moves down by `d × tan(skew-y)`), turned by `rotation` degrees clockwise on the screen (with `y` down, `(u, v)` goes to `(u cos a − v sin a, u sin a + v cos a)`), put back at the origin, and moved by `x` across and `y` down. The order is scale, slant, turn, move.
4. **Nested moves.** An element inside a moving element is moved by its own map and then by its parent's: the map of its picture in the frame is the parent's map times its own. Its origin is worked out from its own rectangle, as if nothing moved.
5. **Layout.** Moving, scaling, turning, slanting and fading never change a place or a size of section 4.1, 4.3 or 4.4: the neighbours of a moving element, and its parent, are placed as if it did not move.
6. **Fading.** `opacity` is clamped to 0 to 1. An element with an opacity below 1 is drawn with all its children into a layer of its own, transparent at first; the layer is then laid over the picture, each of its premultiplied values times the opacity, rounded to the nearest whole level, halves up, by the src-over operation: the element and its children fade as one picture, and where they overlap the one below does not show through. At opacity 0 nothing of the element is drawn.
7. **Drawing under a map.** An element whose map is the identity and whose opacity is 1 is drawn as section 4 gives. A map that only moves by whole pixels moves the element's rectangles and glyphs by that much, and the picture is the same as for an element written there. Any other map draws the element's fills and glyphs with their outlines mapped, filled by vello_cpu 0.3.0 with its anti-aliased coverage (the share of each pixel the mapped shape covers), and blended by src-over. A glyph's outline is never hinted, on either renderer and under any map, the identity included: it is taken from the font as designed, scaled to its size and mapped, so a text that grows or moves by part of a pixel follows its map smoothly and nothing changes in its shape when a turn passes 0 (the glyph runs of vello_cpu hint by default, and the renderers turn that off). A shadow of a text is offset in the text's own coordinates and mapped with it, and its blur is scaled by the square root of the absolute determinant of the map's linear part; an outline is stroked in the text's own coordinates, so its width is mapped too; a colour picture of an emoji is mapped and sampled bilinearly.
8. **Clip.** An element on a canvas shown from another file is cut to that canvas's rectangle in the frame, after its map (`timeline.md` section 4).
9. **Window.** A moving element is drawn in the frames of its window and no other (section 4.2), with its children.
10. **A turn in space** (`notation.md` section 7.8; decision A23; the perspective projection of plane geometry, written out here by us). An element with a `perspective` `P` (pixels, above 0) is turned in space by its `rotate-x` `a` and `rotate-y` `b` (degrees, the values at the frame by rule 1, `0` when not written). Without a `perspective`, `rotate-x` and `rotate-y` change nothing, and the frame is the one without them. With both `a` and `b` exactly 0 the element is drawn as if not turned.
    - **What is turned.** The element is drawn first as rules 6 and 7 give, with its children, its map and its opacity, into a transparent picture of the frame's size: the flat picture. The turn acts on that picture; the cut of rule 8 is applied after the turn.
    - **About what.** The turn is about the point `Q`, the element's origin (rule 2) taken by its map in the frame (rules 3 and 4), which is where the origin is drawn. The eye is `P` pixels straight above `Q`.
    - **The turn.** A point `p` of the flat picture, with `(u, v) = p − Q`, is turned first about the level line through `Q` by `a`, then about the upright line through `Q` by `b`: it goes to `X = u cos b + v sin a sin b`, `Y = v cos a`, and comes towards the eye by `Z = −u sin b + v sin a cos b` (a positive `a` takes the top edge away from the eye, a positive `b` the right edge). It is drawn at `Q + (X, Y) × P ÷ (P − Z)`.
    - **Edge-on, or at the eye.** When `|cos a × cos b|` is at most `10⁻¹²` the element is edge-on and nothing of it is drawn. When a corner of the element's rectangle, taken by its map, comes to the eye or behind it (`P − Z` of 0 or less), nothing of it is drawn.
    - **From behind.** Turned past 90 degrees about either line, the element is drawn mirrored, as the turn above gives it (decision A23); its back is not hidden.
    - **The pixels.** For each pixel of the frame, the point of the flat picture drawn at the pixel's centre is found by the inverse of the turn. When that point's `P − Z` is above 0, the turned picture's value there is taken from the four pixels of the flat picture around it, weighted by their nearness (bilinear, with pixel centres at half pixels, and a pixel outside the frame transparent), each of the four premultiplied values rounded to the nearest whole level, halves up. It is laid over the picture by src-over, as rule 6 lays a layer.
    - **Nested.** The flat picture of a turned element is drawn in the frame, its parents' maps included, and the turn acts on it there. An element inside a turned element is part of its flat picture and keeps no depth of its own.
    - **Tests.** `crates/draw/tests/turn_in_space.rs` (the map, its inverse, edge-on, a corner at the eye); `crates/render/tests/turn_in_space.rs` (edge lengths, edge-on and mirrored, the order of the two turns, no perspective, on both renderers); `crates/render/tests/turn_fixture_checked_in.rs` (fixture `turn-in-space`, frames 0, 15, 30 and 45, to the byte); `crates/cli/tests/perspective_reports.rs` (a perspective of 0 or below, `FS-0053`).
11. **Blur and brightness** (`notation.md` section 7.6; the Gaussian function of probability theory, written out here by us). An element with a `blur` above 0, or a `brightness` other than 1, is drawn with all its children into a layer of its own, as rule 6 draws a fading one, and its picture there is blurred, then brightened, before it is cut (rule 8 and the clip of a set of columns or a canvas), faded (rule 6) and laid over the picture. A turned element (rule 10) is turned after them: its flat picture is the blurred and brightened one.
    - **The values.** `blur` is a number of 0 or more, the standard deviation of the blur in the element's pixels; `0`, the default, leaves the picture as it is. `brightness` is a number of 0 or more; `1`, the default, leaves the picture as it is. Either below 0 is reported with its line as `FS-0034`, and nothing is drawn (section 3). This version takes both as attributes written on a `<box>` or a `<text>`; a `<tween>` or a `<set>` that changes them is refused as rule 1's properties are (`FS-0035`).
    - **In the frame.** The standard deviation `σ` in pixels of the frame is the `blur` times the square root of the absolute determinant of the linear part of the element's map in the frame (its own map after its parents', rule 4), as rule 7 scales the blur of a shadow. A `σ` of 0 leaves the picture.
    - **The blur.** The layer is taken as a picture whose premultiplied values are constant over each pixel, and transparent outside the frame. It is blurred across, then down, each time with the same weights: the pixel `k` pixels away from the one worked out (`k` a whole number, `|k|` at most `R = ⌈4σ⌉`) counts with the weight `Φ((k + ½) ÷ σ) − Φ((k − ½) ÷ σ)`, where `Φ` is the distribution function of the standard normal distribution, the weights divided by their sum. That is the blur by a Gaussian of standard deviation `σ` of the picture so taken, read at the pixels' centres, without the tails beyond `R + ½` pixels (less than 0.0007 % of the weight). What lies outside the frame is not part of the layer: the blur takes it as clear.
    - **The brightness.** Each premultiplied colour value `c` of a pixel of the blurred layer, with its alpha `α`, becomes `min(c × brightness, α)`: the colour is multiplied by the brightness and stops at white, and the alpha does not change. Values are kept unrounded through the blur and the brightness, then each is rounded to the nearest whole level, halves up.
    - **Fading as one picture.** The layer holds the element and all its children drawn together, one over another by src-over, before it is faded: where two children overlap, the one below does not show through the one above, and the overlap is as strong as the rest. At opacity 0 nothing of the element or its children is drawn, whatever its blur and brightness.
    - **Tests.** `crates/draw/tests/blur_weights.rs` (the weights against the normal distribution); `crates/render/tests/blur_and_brightness.rs` (the values across a blurred edge against a Gaussian worked by hand, halved and stopped colours, the order of the two, an element faded as one picture, opacity 0, on both renderers); `crates/render/tests/blur_fixture_checked_in.rs` (fixture `blur-and-brightness`, to the byte, and its pictures held to worked values); `crates/cli/tests/blur_reports.rs` (a negative blur and a negative brightness, `FS-0034`).

### 4.6 Backgrounds

Sources: `notation.md` section 7.4 (the forms of `background`, `background-size`, `background-position` and `background-repeat`); the gradient lines and shapes of CSS Images Level 3 (W3C), whose names and meanings the notation takes, written out here in our own words; the proofs' record `native-notation-reference.md`, read for behaviour under decision B4; decision P13 (radial gradients in Sprint 1, conic gradients in Sprint 5).

A `<box>` draws its `background` as layers. One opaque colour is drawn as section 4 gives (rule 2 of the picture); anything else is drawn by the rules below. The background of the root stays one opaque colour, and a `background` of any element other than a `<box>` stays refused (section 3).

1. **Layers.** `background` is a list of layers separated by commas at the top level (a comma inside a gradient's brackets does not separate layers). The first listed is on top: the layers are drawn last listed first, each over what is there. A layer is a colour (`#rrggbb` or `#rrggbbaa`), a linear gradient or a radial gradient.
2. **The settings of the layers.** `background-size`, `background-position` and `background-repeat` are each a list separated by commas with one entry for every layer, in the order of `background`, or one entry for all. When not written, every layer takes `auto`, `0 0` and `repeat`.
   - Size: `auto`, the box's own width and height, or `W H`, each a number of pixels (0 or more) or a percentage of the box's width (`W`) or height (`H`).
   - Position: `X Y`, each a number of pixels, the offset of the tile's top left corner from the box's, or a percentage `p` of the room left over, `(box − tile) × p ÷ 100` (`50%` centres the tile, `100%` puts it against the far edge).
   - Repeat: `repeat`, the tile laid side by side in both directions from its place until the box is covered, or `no-repeat`, the tile drawn once.
3. **The tile.** A layer is drawn in a tile of its size at its place, measured from the box's top left corner. A point of the box at `(x, y)` from that corner lies in the tile at `(x − X) mod W` across and `(y − Y) mod H` down when the layer repeats (the remainder taken 0 or more), and at `(x − X, y − Y)` otherwise, where it shows only when it lies in `0 ≤ u < W` and `0 ≤ v < H`. A tile with a size of 0 on either side draws nothing. A layer never shows outside the box.
4. **The colour of a pixel.** Each pixel is taken at its centre, `(x + 0.5, y + 0.5)` from the box's top left corner. A colour layer has its colour everywhere in its tile. A gradient gives a place `t` on its line (rules 5 and 6), in pixels, and the colour at `t` from its stops (rule 7).
5. **Linear gradient.** The angle `a` is in degrees: 0 points up, 90 right, 180 down, and 180 when it is not written. For a tile of `W` by `H` the line runs through the tile's centre in the direction `(sin a, −cos a)` and has the length `L = |W sin a| + |H cos a|`, so that its ends are the corners the direction meets first and last. Its start is the centre less half the length along the direction, and `t` is the distance from the start along the direction: `t = (u − W/2) sin a − (v − H/2) cos a + L/2`.
6. **Radial gradient.** The centre is `at X% Y%` of the tile's width and height, or the tile's middle. The radii `rx` and `ry` are:
   - `circle R`: both `R` pixels; `ellipse A% B%`: `A%` of the tile's width and `B%` of its height;
   - `circle`: both the distance from the centre to the farthest corner of the tile;
   - `ellipse`: `√2` times the distances from the centre to the farther side across and the farther side down, which is the ellipse of that shape through the farthest corner.

   With the point at `(du, dv)` from the centre, `t = rx × √((du / rx)² + (dv / ry)²)`: the line is the radius across, and a stop of a share is a share of `rx`. A radius of 0 is not in the form (rule 10).
7. **Stops.** A stop's place is pixels from the line's start, or a percentage of the line's length (`L` for a linear gradient, `rx` for a radial one). A place less than the one before it is taken as the one before it, so that the places never go back. Before the first stop's place the colour is the first stop's; from the last stop's place on it is the last's. Between two stops with places `p₀ < p₁`, at `t` with `p₀ ≤ t < p₁`, the colour is `c₀ + (c₁ − c₀) × (t − p₀) ÷ (p₁ − p₀)`, worked on the colours with each channel multiplied by its alpha (premultiplied), so that a stop of a fully transparent colour fades the colour away without darkening it. Two stops at one place make a hard edge: at that place and after it the later stop's colour holds.
8. **Laying a layer.** The colour of a layer at a pixel, premultiplied, each of its four values from 0 to 1, is made 8 bits by `⌊255 v + 0.5⌋`, and laid over the pixel by src-over: each value of the pixel becomes the layer's value plus the pixel's value times `(255 − α) ÷ 255`, rounded to the nearest whole level. The layers are laid one at a time, the last listed first.
9. **Under a map.** A box that moves by whole pixels draws its layers in its moved rectangle, as if it were written there. Under any other map (section 4.5, rule 7), each frame pixel the mapped rectangle covers is taken back through the inverse of the map to the point of the box it shows, its colour is found there by rules 3 to 7, multiplied by the share of the pixel the mapped rectangle covers (the coverage of rule 7 of section 4.5), and laid as rule 8 gives. A map that flattens the box draws nothing.
10. **What is reported.** Each with the line of the attribute, and when a style gives it, the style's name:
    - a layer, a size, a position or a repeat that is not in the forms above, a gradient with fewer than two stops, a stop with no place, a shape that is not one of rule 6, a radius of 0 or less, a size below 0: `FS-0064`, invalid, with the form taken;
    - a `background-size`, `background-position` or `background-repeat` list with neither one entry nor one for each layer: `FS-0065`, invalid, with the number of layers;
    - a `background-size`, `background-position` or `background-repeat` on a box with no `background`: `FS-0066`, invalid;
    - `conic-gradient(...)` as a layer: `FS-0035`, unsupported (`notation.md` section 14, S17).

### 4.7 Shadows

Sources: `notation.md` section 4 (the form of a shadow: `X Y BLUR COLOUR`, four values, no spread and no `inset`), section 7.5 (`box-shadow`: a list, the first listed on top, following the box's corners, its blur counted as CSS counts it) and section 7.6 (`drop-shadow`: the finished picture's alpha, blurred, moved and coloured, under the picture; the blur's method); CSS Backgrounds and Borders Level 3 (W3C), section 7.1, for what a box shadow is: the shape of the box's border edge, moved by the offset, blurred with a standard deviation of half the blur, and seen only outside the box's border edge; Filter Effects Module Level 1 (W3C), `drop-shadow()`, for a shadow of the alpha of a finished picture. The method of the blur is the one `text.md` section 6.6 rule 5 gives for a shadow of text, which is ours.

1. **The form.** A shadow is four values separated by spaces: the offset across `X` and the offset down `Y` (numbers of pixels, either sign, with an optional `px`), the blur `B` (a number of pixels, 0 or more) and the colour (`#rrggbb`, or `#rrggbbaa` with `aa` equal to `ff`). `box-shadow` is a list of such shadows separated by commas; `drop-shadow` is one. `box-shadow` is taken on a `<box>`; `drop-shadow` on a `<box>`, a `<text>` and a `<composition src>`.
2. **The blur.** A shadow's alpha plane is blurred with the standard deviation `sigma = s × B / 2`, where `s` is the scale of the element's map (rule 7): `s = √|ad − bc|`, 1 when the element is not moved or moved only. The blur is three passes of an average, each over a span of `floor(sigma × 3 × √(2π) ÷ 4 + 0.5)` pixels, across the picture and then down it, each average rounded to the nearest whole level, a half up, and a pixel outside the frame counting as clear: the method of `text.md` section 6.6 rule 5. A span below 2 leaves the plane as it is, so a blur of 0 gives a hard edge.
3. **A box shadow.** The shape of the box is its outer edge, its rectangle with its corners rounded by its `border-radius` (`box-edges.md` section 3), under its map: the coverage of each frame pixel by the mapped shape, as `box-edges.md` gives it, an alpha plane of the frame from 0 to 255. The shadow's plane is the coverage of that shape moved by `X` and `Y` in the box's own pixels and then mapped, as a shadow of text moves its glyphs (`text.md` section 6.6 rule 5), then blurred (rule 2). Each value of the plane is then multiplied by `255 − ` the coverage of the box's own shape at that pixel, divided by 255 and rounded (a half up): a shadow is seen only outside the box, so a box with a background that is not opaque does not show its shadow through it. The plane is laid in the shadow's colour: each pixel becomes `colour × a ÷ 255` plus the pixel times `(255 − a) ÷ 255`, rounded, for the plane's value `a`.
4. **The order.** A box's shadows are drawn before its background, the last listed first, so that the first listed lies on top (`notation.md` section 3, the drawing order). Each is laid on its own.
5. **A shadow that follows.** `drop-shadow` takes the finished picture of the element: everything it draws and everything inside it, drawn together with the element's own map and turn in space, before its cut and its opacity (`notation.md` section 7.6). The shadow's plane is the alpha of that picture, moved by the offset under the map's turn and scale, `(aX + cY, bX + dY)` frame pixels, each rounded to the nearest whole pixel (a half up), as `displace` rounds its distance (`notation.md` section 7.6), then blurred (rule 2), and laid in the shadow's colour as rule 3 lays it, under the picture: so the shadow follows the outline of what is drawn, and not the element's rectangle. The picture is then laid over it, and the two together are cut and faded as one group. Where the picture is opaque the shadow does not show; where it is partly clear the shadow shows through it.
6. **Who draws it.** Both kinds are drawn by the processor's renderer, into a plane the size of the frame; the card's renderer lays that picture on its frame as it lays a shadow of text (`card-renderer.md`), so the two renderers agree (`notation.md` section 7.6).
7. **Under a map.** The map is the element's map at the frame (section 4.5). Moved by whole pixels, the shadow moves with the box, and `s` is 1.
8. **What is reported.** Each with the line of the attribute:
    - a shadow written with the word `inset`: `FS-0035`, unsupported (`docs/spec/notation.md` section 14, S73: an inner shadow; waits until Sprint 5);
    - a shadow of five values, the fourth a length (a spread): `FS-0035`, unsupported (section 14, S74: a shadow with a spread; waits until Sprint 5);
    - a colour with an alpha below `ff`: `FS-0035`, unsupported, as for a shadow of text (section 14, S75);
    - a blur below 0: `FS-0034`, invalid, `must be 0 or more`;
    - any other value that is not in the form of rule 1, or a `box-shadow` that is not a list of such shadows: `FS-0070`, invalid, with the form taken.
9. **Tests.** `crates/draw-cpu/tests/box_shadows.rs` and `crates/render/tests/shadows_worked_by_hand.rs` (the place, the fade, the hard edge, the order, the outline of a group of two children, on both renderers), `crates/render/tests/shadows_fixture.rs` (the fixture `shadows` against its checked-in pictures and the card's agreement), and `crates/cli/tests/shadow_reports.rs` (the reports of rule 8).

### 4.8 Footage

Sources: `notation.md` sections 6.7 (`<video>`), 5.3 (the source picture of a clip's first frame, decision A22), 7.1 (a `<video>` must be given both sizes), N3 (the kinds read) and N4 (a source shorter than its clip); `frx7/docs/spec/os-codecs.md` section 5 (the pictures of a track asked for by their number) and `frx7/docs/spec/pixel.md` sections 1, 7, 8, 10 and 12.1 (a picture brought to another size, planes to red, green and blue by the standard the source names, a source that names none, and the worked values of white, black and mid grey); decision A12 (the test clips are made by frx7's writers); decision A29 (the stated method of "no other program started"). The proofs' record `native-render-pipeline.md` was read for behaviour under decision B4.

1. **What is drawn.** A `<video>` in the root, or in a `<box>` that lays out no row, column or set, whose `src` names a file of H.264 pictures of 8 bits in a file of the MP4 family, is drawn as footage in its box: the box of section 4.1, placed by `left`, `top`, `right`, `bottom` and sized by its `width` and `height`, which are required and are whole numbers of 2 or more (`notation.md` section 7.1). It is drawn in the frames of its window (section 4.2), and in no other frame. Its sound is not read and is not heard in the film (`notation.md` section 14, S08).
2. **Which picture.** On frame `n` of its window, which begins at frame `f`, the footage shows the source picture numbered `n − f`, the pictures numbered from 0 in the order they are shown (section 5.3 with `media-start` 0: the first frame of the clip shows the first picture, and each later frame the next). Where `n − f` is past the source's last picture, the last picture holds (N4). The source's own frame rate does not change which picture is shown in this version; a frame shows the picture with its number in the clip.
3. **Colour and size.** The picture is brought to red, green and blue of 8 bits by frx7's arithmetic (`pixel::convert`), by the colour standard and range the stream names, or by frx7's rule for a stream that names none (`pixel.md` section 10); then, when its size is not the box's, to the box's width and height by frx7's arithmetic (`pixel::resize`, `pixel.md` section 1), whatever the source's own size and shape: the footage fills its box. White, black and mid grey of the source are then the values of `pixel.md` section 12.1. Every pixel is opaque.
4. **Drawing.** The footage is one mark of a picture (`draw::Mark::Picture`) with its top-left corner at the box's, drawn one pixel for one, by src-over with premultiplied values: an opaque picture replaces the pixels under it. The part outside the frame is not drawn; on a canvas shown from another file it is cut to that canvas, as a box is (`timeline.md` section 4). Under a map that is not a move by whole pixels a picture is drawn through the map and sampled bilinearly, as the colour pictures of a paragraph are (section 4.5, rule 7); a `<video>` itself does not move in this version (section 3).
5. **When the sources are opened.** Before the first frame is drawn, every source the scene shows is opened through frx7 and its first picture is decoded (`notation.md` N3), by the system's own decoder, in the process: no other program is started. A source that cannot be opened or decoded stops the render before the first frame with the report of `FS-0036`, ``the video could not be made: `clips/a.mp4` could not be opened: <the reason frx7 gives>``, and no file is written. The reports of a source that is missing, damaged or of a kind not read come with their own ticket (T089), which `check` lists too.
6. **Reports of the notation** (`check-command.md` section 3a), on the line of the element for a missing attribute and on the attribute's line for a value: a `<video>` with no `width` or no `height`, or one below 2: `FS-0085`, ``<video> needs the attribute `width`, a whole number of 2 or more: footage is stretched to its box``, ``` `width` of a <video> must be a whole number of 2 or more, not 1 ```; a `<video>` with no `src`: `FS-0086`, ``<video> needs the attribute `src`, the path of its file from the project folder``. A size that is not a whole number is `FS-0032` (``` `width="10.5"` is not a whole number ```).

## 5. The film

The frames, numbered 0 to the frame count less 1 (`notation.md` section 5.1), are drawn in order on the processor, brought to the form the encoder takes and handed to frx7, which encodes them and writes the file. Nothing else is started.

- **Colour.** A frame is converted from red, green and blue to luma and chroma in 4:2:0, 8 bits, with the matrix of BT.709 and the narrow range, by frx7's own arithmetic (`pixel::convert`, `frx7/docs/spec/pixel.md`), and the file is marked BT.709. Alpha is not used: a finished frame is opaque.
- **The stream.** H.264, 8 bits, the composition's width and height, the composition's frame rate (a whole number of frames a second), through the system's own encoder, hardware first when the machine has one (decision D22), at a quality of 0.65 on a scale from 0 to 1, which is what `render.quality: standard` asks for, with a key picture at least every two seconds and pictures that may be encoded out of the order they are shown in.
- **The file.** An MP4 with one video track and one sound track (section 5.2), written by frx7's MP4 writer. It is written in a staging place beside the output path, and moved to the output path only when the last frame and the sound are written (section 6, decision P5). An earlier file at the output path is not touched by a render until that moment, and a render that fails removes its staging file and leaves the earlier file as it was.
- **One thread draws and encodes, frame after frame.** Several workers, and drawing and encoding at the same time, are later tickets.
- **Exactly the frames the length calls for.** The track holds exactly the frame count of `notation.md` section 5.1: the root's `duration` times its `fps`, taken as the whole number when it is within 0.001 of one and rounded up otherwise, at least 1. No frame is added at the end and none is dropped. Five seconds give 120 frames at `fps="24"`, 150 at `fps="30"` and 300 at `fps="60"`; `duration="1.01"` at 30 gives 31 (30.3 is rounded up) and `duration="1.00001"` at 30 gives 30 (30.0003 is within 0.001 of 30). The track's frame rate is the root's `fps` (30 when it is not written), as a whole number of frames a second over 1. The count `check` prints (`check-command.md`), the `frames` line of the summary (section 7) and the number of pictures in the file are the same number, because all three are the one frame count of the scene.

### 5.1 The form of the finished file

What a player needs to show the film correctly and to start it before it is fully loaded. Sources: ITU-T H.264 (the sequence parameter set: `bit_depth_luma_minus8`, `chroma_format_idc`, and the colour description of its VUI, Annex E); ITU-T H.273 Table 2 to 4 (the code point 1 for BT.709 primaries, transfer and matrix); ITU-R BT.709-6 (the narrow range: luma from 16 to 235, chroma from 16 to 240); ISO/IEC 14496-12 (the top-level boxes `ftyp`, `moov` and `mdat`, the sample table and its sync samples, the composition time offsets); decision D22 of `DECISIONS.md` (a key picture at least every two seconds, reordering); decisions A10 (the standard player) and A29 (a tolerance the ticket calls stated is stated here); decision B6 (whether pictures are reordered is read from the sample times when the headers are silent); `frx7/docs/spec/os-codecs.md` (key distance in time, and what the system's encoder was measured to keep of flat pictures); `frx7/docs/spec/pixel.md` section 12.1 (the worked values of white, black and mid grey). The proofs of concept's `native-render-pipeline.md` (a record, decision B4) asked for the same form, taken as behaviour.

- **The stream.** H.264 whose own headers say 8 bits of luma and of chroma, chroma in 4:2:0, not interlaced, and the colour description of BT.709: primaries 1, transfer 1, matrix 1, narrow (limited) range. The track of the file carries the same marks. `frx7 probe` shows them on the track's line and on its `headers:` line, read by frx7's own code.
- **The tables in front.** The file's top-level boxes are, in this order, `ftyp`, `moov` (the tables: what the samples are and where they lie), and then `mdat` (the media). A box of free room may lie between `moov` and `mdat`. No `moov` follows the media. A player can therefore read the tables and start before the file is fully loaded. frx7's MP4 writer keeps room for the tables in front because the render tells it, before the first picture, how many pictures the track will hold (the frame count of section 5).
- **Key pictures.** The first picture of the film is a key picture (a sync sample, at which decoding may start). The encoder is asked for at most `key_distance_within(2.0, fps)` frames from one key picture to the next: the most whole frames that fit in two seconds (48 at 24, 60 at 30, 120 at 60). In the written file no two key pictures that follow one another are further apart than two seconds in the times they are shown; the encoder may put a key picture sooner.
- **Reordering.** Pictures may be encoded out of the order they are shown in (B frames), and they are: in the written file some picture is shown later than a picture decoded after it. The system's encoder writes no statement of reordering in the headers, so `frx7 probe` gives the answer from the sample times and says so (`pictures reordered (from the sample times)`, decision B6).
- **Plays in the standard player.** The file opens in the system's media framework, which says it is playable, and every picture decodes to the end, in the order of increasing times, as many pictures as the frame count. This scripted decode stands for the standard player (decision A10).
- **Flat colours read back.** The conversion of section 5 gives, for an opaque colour with red, green and blue equal, Cb and Cr of 128 and the luma of BT.709's narrow range: white `#ffffff` gives Y 235, black `#000000` gives Y 16, and mid grey `#808080` gives Y 126 (16 + 219 x 128 / 255 = 125.93, rounded). **Stated tolerance (decision A29):** inside a flat box whose edges lie on the 16-pixel grid of the encoder's blocks (its `left`, `top`, `width` and `height` are multiples of 16), at least 4 pixels from its edges, in a film of at least 96 by 64 pixels, every luma and every chroma sample of every picture decoded from the file is within **2 levels** of those values. Source: `frx7/docs/spec/os-codecs.md`, "What the software H.264 encoder was seen to do": from 96 by 64 up every flat picture was within two levels of what was asked with the encoder on the processor, and within one with the hardware encoder. The 4 pixels keep the edge of a box, where a lossy encoder spreads one colour into the next, out of the measure. A box off the grid shares a block with its surroundings, and there the encoder spreads the colour of the surroundings further in: measured with boxes of 32 by 32 at `top="38"` on a canvas of `#204060`, Cb lay up to 4 levels off in the samples 4 and 5 pixels inside the box's lower edge, in some pictures of a film of one second at 30 frames a second, so the tolerance is stated for boxes on the grid only. On the grid the most was 1 level, for each of the three boxes, over every picture of that film (`crates/render/tests/standard_mp4_form.rs`).

A failure of frx7 or of the machine after the first frame (the encoder refuses the stream, the file cannot be written) ends the run with `FS-0036`: `FS-0036: failure: the video could not be made: <reason>. <remedy>`, then the line `Failed: the video could not be made`, and the exit code 1. A folder that cannot be made or written is refused before the first frame, as section 6 says.

### 5.2 The sound track

Every film holds exactly one sound track, whether the composition has sound or not: players and editors treat a file with no sound track differently from a file whose sound is silent. Sources: ISO/IEC 14496-3 (AAC-LC, packets of 1,024 sample frames); ISO/IEC 14496-12, clauses 8.6.5 and 8.6.6 (the edit list, which leaves the encoder's lead-in out and ends the track at the last real sample); `frx7/docs/spec/os-codecs.md` section 3.1 (AAC through the system's encoder at a constant bit rate, its lead-in, its read-back to the sample, and the bit rate it was measured to keep); `frx7/docs/spec/mp4.md` section 2.2; decision A29 of `DECISIONS.md` (the AAC bit-rate margin) and A10 (the standard player). The proofs of concept's `native-render-pipeline.md` (a record, decision B4) gave the mix as 48,000 samples a second in two channels, as long as the film to the sample, taken as behaviour.

- **The mix.** The `mix` crate makes the sound of the film: 48,000 sample frames a second, two channels (left, then right), 32-bit floating point. Each `<audio>` of the composition is placed in it to the sample, read from its source through frx7 (`sound.md`); where no sound plays, the sample is 0, silence.
- **Its length.** The picture's length in seconds, the frame count over the frame rate (section 5), times 48,000, rounded to the nearest sample frame, a half up. At a frame rate that divides 48,000 (24, 30, 60 and the like) it is exact: 5 seconds at 24, 30 and 60 frames a second are 240,000 sample frames; 31 frames at 30 are 49,600.
- **Handed over with the frames.** After each frame is handed to the picture encoder, the mix up to the end of that frame (the length of frames 0 to that one, by the rule above) is handed to the system's AAC encoder through frx7's `codec` interface, and its packets are written into the same file, so that picture and sound lie side by side in it.
- **The form.** AAC-LC, 48 kHz, two channels, at a constant bit rate: `render.audio-bitrate` in kbit/s (1 kbit/s is 1,000 bits a second), **192 kbit/s** when it is not written (section 1.1; values outside 64 to 320 are refused before the first frame, section 3). The track's timescale is 48,000; frx7's writer marks the encoder's lead-in in the edit list, so that the track's length, and the sound read back from it, is the mix's length to the sample. `frx7 probe` shows it as a `sound, aac, 48000 Hz, 2 channels` track with the sample entry `mp4a`.
- **Silence read back.** Every sample of a silent mix that is read back from the track through frx7's sound reader is 0.
- **The bit rate (stated, decision A29).** The track's bit rate, the bytes of all its packets over its length (as `frx7 probe` gives it), is **within 10 % of the rate asked for**: from 172,800 to 211,200 bits a second at the default 192 kbit/s, from 115,200 to 140,800 at 128 kbit/s. Measured on a silent track of renders at 30 frames a second: about 196 kbit/s for 2 seconds and within the margin for 1 and 10 seconds (`crates/render/tests/silent_sound_track.rs`); frx7 measured about 193 kbit/s over ten seconds and about 200 kbit/s over one, where the packets of the lead-in weigh more.
- **Plays.** The system's media framework opens the file as playable, decodes every picture to the end and reads the sound track to its end (decision A10).
- **A refusal.** The AAC encoder is started before the file is made; an encoder that refuses ends the run with `FS-0036` as below, and no file is left.

### 5.3 The codec of the picture

`render.codec`, or `--codec` (section 1), chooses the codec the picture is encoded in: `h264`, the default, or `hevc`. Sources: the ticket T084 of Sprint 1; ITU-T H.265 (the stream); ISO/IEC 14496-15, clause 8.3.3.1 (the `hvcC` record: the general profile in the low five bits of byte 1, the chroma format in the low two bits of byte 16, the luma and chroma bit depth less 8 in the low three bits of bytes 17 and 18) and clauses 8.4.1 and 8.4.2 (the sample entries `hvc1` and `hev1`); `frx7/docs/spec/mp4.md` sections 2 and 3.2 and `frx7/docs/spec/os-codecs.md` section 6 (what frx7's writer and the system's encoder give); decision A10 (the standard player).

- **HEVC of 8 bits.** With `hevc` the picture is encoded by the system's HEVC encoder through frx7, with the same settings as H.264 (section 5.1): 8 bits, 4:2:0, the quality of `standard`, a key picture at least every two seconds, reordering, and the colour description of BT.709 with the narrow range. The profile is Main (general profile 1). HEVC of 10 bits and of a high dynamic range is not written in this version.
- **The mark players expect.** The track's sample entry is `hvc1`, with the parameter sets in its `hvcC` box, and `hvc1` is among the compatible brands of `ftyp`. `frx7 probe` shows `hevc` on the track's line, `sample entry: hvc1` under it, and 8 bits on its `headers:` line. The system's media framework takes a file marked `hvc1` and refuses the same file marked `hev1` (`frx7/docs/spec/os-codecs.md` section 6.5), so the mark is what makes the file play in the standard player.
- **The rest of the film is the same.** The frames drawn, their count and their marks (section 7.1), the sound track (section 5.2), the tables in front and the key pictures do not depend on the codec: only the encoding of the pictures differs. The file plays in the standard player as section 5.1 states, with its sound to the end.
- **Another value** is not a codec of this version: it is refused when the options or the project file are read, with the values taken (section 1, and `project-file.md` section 5), and nothing is drawn or written.
- **The summary** names the codec used on its `codec` line (section 7).

## 6. The place of the finished file, and what the author's files are

- The finished file is, by the rule of section 1.1: the path of `--output`; else `render.output` of the project file; else `<paths.renders>/<name>.mp4`, with `paths.renders` (default `renders`) and `name` (default the folder's name) as `project-file.md` sections 3 and 6 say. A relative path, the option's included, is taken from the project folder, never from the folder the command is run from (`project-location.md` section 4); a path that begins with `/` is taken as it is. The folder it is to be in is made when it is missing, with every folder above it that is missing, and is left in place when the render then fails.
- **The film's extension.** A film is written to a path ending in `.mp4` or `.m4v`. A path ending in `.mov`, or in an extension no writer of this build claims, is refused before the first frame, with no file left at the path. The support table's S34 will report such a path (B40), once T086 builds it; until then the refusal comes from the container's making, as `FS-0036`.
- **Staging.** The film is written to a staging file in a hidden folder beside the output path, named `.framesmith-<pid>` after the process id of the run. The staging file is named by the output's name with `.part` added before its extension, which keeps the container (`film.mp4` gives `.framesmith-<pid>/film.part.mp4`). Before it makes the hidden folder, the run creates, beside the output path, a lock file named `.framesmith-<pid>.lock` that is already held by an exclusive lock: the file is created and locked in one step, so no other render can see it unlocked. Only then does the run make the hidden folder, and the folder holds nothing of any earlier run, since the lock is the run's own. The lock is held for the whole render. When the render ends, whether it completes or fails, the run removes its hidden folder, then its lock file, and releases the lock. A hidden folder that cannot be removed keeps its lock file beside it, so that the sweep takes both later. The film is moved to the output path, replacing any file there, only when the last frame and the sound are written and the file is closed. The move is one rename, from the hidden folder to the output path, so the output path holds either the earlier file with its bytes unchanged or the new whole file, never a file that is still being written.
- **A failed render keeps the earlier file.** When the render fails or is cancelled, its staging file is removed and a file already at the output path keeps its bytes. A render that fails before its first frame writes nothing at the output path.
- **A killed render.** A render killed outright (`SIGKILL`, a crash, a power cut) removes nothing. Its lock file stays beside the output, with its hidden folder if it had made one, and the output path keeps what it held before, since the film is moved there only on completion. The next render into the same folder first sweeps: for each lock file `.framesmith-<pid>.lock` whose lock it can take, it removes the hidden folder `.framesmith-<pid>` of that run, if there is one, then the lock file, and logs that it did (`run-log.md`). The operating system releases a lock when its process ends, however it ends, so a lock that can be taken belongs to a render that no longer runs. The sweep decides by the lock alone and never by the process id in a name: a lock left by a render whose process id a live process has since taken is removed too. A lock that is held is never touched, so two renders into one folder do not disturb each other. The sweep does not ask the system whether a process runs. Every point at which a render can be killed is covered: the lock file exists before any hidden folder does, so no folder is ever left without its lock file. The next render then completes and leaves no hidden folder and no part file of the killed run.
- **An output place that cannot be written is refused.** Before the first frame, the folder of the output path is made when it is missing, and a staging file is opened for writing in the hidden folder of the run, under the run's lock, and removed again with the lock file (section 6, Staging). When either fails, nothing is drawn and the command reports `FS-0072` (`error-catalogue.md`, section 4) with the path and the system's reason, and the closing line `Refused: the video was not made, because its folder cannot be written`; it exits 2 (decision A19). The remedy names `--output`. A failure after the first frame is `FS-0036`, exit 1, as before.
- **The kind of the finished file.** A finished file whose name does not end in `.mp4` or `.m4v` is refused before any frame, as unsupported (support table S34), whether `--output` or `render.output` gives it; the message names the option or the project file's line as written.
- **A refused render writes nothing.** A render refused for what is invalid or unsupported makes no frame and leaves no staging folder of its own (B60), and a file already at the finished file's path keeps its bytes (`check-command.md` section 3d). It still sweeps the staging folders of renders killed outright (Staging above): into a folder that holds them, a refused render leaves none.
- **The author's files are not touched.** The composition, the project file and every other file of the project have the same bytes after the run as before. Options change nothing in them: `framesmith.yaml` is never written. The things a run adds are the finished file, its folder when it was missing, and the run log under the folder the command is run from (`run-log.md` section 1).

## 7. The summary

A render that completes prints, on standard output, these lines, in this order, and ends with the exit code 0:

```
Rendered demo/renders/demo.mp4
frames: 150
size: 1280x720
frame rate: 30 fps
length: 5.000 s
renderer: processor
output: renders/demo.mp4 (default)
backend: cpu (option)
quality: standard (project file)
encoder: hardware (default)
codec: h264 (default)
workers: auto (default)
audio bitrate: 128 kbit/s (project file)
elapsed: 1.234 s
```

- The first line is the word `Rendered` and the path of the finished file: the project folder as it was written on the command line (or the folder found from the file written there), joined with the path of the file. `framesmith render demo` prints `demo/renders/demo.mp4`.
- `frames` is the number of frames written; `size` is `width` by `height`; `frame rate` is `fps` of the root; `length` is the frames divided by the frame rate, in seconds with three decimals; `renderer` is the renderer that drew: `processor` for `cpu`, `card` for `gpu`; for `auto` it is `card (chosen by auto)` when the card started, and `processor (chosen by auto: no suitable card)` when none did (section 1.2; the names are those of `card-renderer.md` section 3); `elapsed` is the seconds the run took from the start of the drawing to the end of the file, with three decimals.
- **The settings used**, one line each, between `renderer` and `elapsed`, in the order above: `output` (the path of the finished file as it is written, before it is taken from the project folder), `backend`, `quality`, `encoder`, `codec`, `workers` and `audio bitrate` (in kbit/s). Each shows the value in use (section 1.1) and, in brackets, where it came from: `option` when an option gave it, `project file` when `framesmith.yaml` wrote it, `default` otherwise. A setting an option changed shows the option's value. `output` is `project file` when the project file wrote `render.output`, `paths.renders` or `name`, the keys it is made from.
- Nothing is printed on standard error.

| Outcome | Standard output | Exit code |
|---|---|---|
| The film is written | The summary above | 0 |
| The project has a report, or there is no project | What `check` prints (section 2) | 1 |
| Every report is of the kind unsupported (the reader's, or `FS-0035`) | The reports and the `Unsupported:` line | 2 |
| A report of `FS-0034`, or of another invalid kind, with or without reports of the kind unsupported | The reports and the `Invalid:` line | 1 |
| The film could not be made | The report of `FS-0036`, then the line `Failed: the video could not be made` | 1 |
| The output folder cannot be made or written, before the first frame | The report of `FS-0072` with the path and the system's reason, then the line `Refused: the video was not made, because its folder cannot be written` | 2 |
| `gpu` is asked for, and no card that frx7 can draw with is there (before the first frame, no file) | The report of `FS-0038`, then the line `Refused: the video was not made, because the graphics card that `gpu` needs is not available` | 2 |
| The command line cannot be read | Nothing (standard error: `check-command.md` section 1) | 1 |

The report of `FS-0038` carries the reason the card gave, which frx7 gives (for example, that this machine has no graphics card frx7 can draw with), and the remedy of the catalogue: the setting to change, `render.backend` or `--backend`, to `auto` or `cpu` (`error-catalogue.md` section 4). Its outcome in the run log is `refused` (`run-log.md` section 4).

### 7.1 The frame marks

With `--marks`, a render that completes prints, after the `elapsed` line, one line for each frame in the order of the frames, `mark <number>: <mark>`, the number in four digits or more as in the checked-in pictures (section 9) and the mark as 16 small hexadecimal digits:

```
mark 0000: 5c1f0e2a9b3d7c41
mark 0001: 5c1f0e2a9b3d7c41
```

The mark of a frame is a short mark of its pixels, equal for equal pixels: the 64-bit FNV-1a hash (Fowler, Noll and Vo, offset basis `cbf29ce484222325`, prime `100000001b3`) of the picture the renderer drew, before it is brought to the encoder's planes, taken over the width and the height, each as four bytes with the lowest first, then the pixels' bytes, red, green, blue and alpha, row by row from the top. It does not depend on the encoder, on the file, or on the time; two frames with one picture have one mark, and a picture that differs in one value has, but for a collision of the hash, another. The marks are printed only when the film is written; a render that stops prints none. The marks compare two runs of one composition: the renderer that drew is on the `renderer` line, and only marks of one renderer are compared.

## 8. A frame on request

`render` draws frames in order. Any single frame can also be drawn on request, with no command for it: the render crate's `Scene` holds a composition ready to draw, and `Scene::picture(number, renderer)` gives the picture of one frame, for the tests of this version and for the preview later (Sprint 3 brings the command). A frame asked for is the picture `render` draws for that number, whatever was asked for before: frames 0, 7 and the last, in that order or in reverse, give the same pictures. A number at or past the frame count is refused, naming the number and the last frame.

**The order proof.** That a frame depends on the composition and its number alone (`PLAN.md`, section 3; `CLAUDE.md`, rule 1) is held by tests that compare frame marks (section 7.1), on the processor's renderer and on the card's:

1. The marks of every frame drawn in order equal, frame by frame, the marks of every frame drawn in reverse order, with one renderer kept from the first frame to the last, so that anything it kept from a frame drawn before would show.
2. Frames asked for in a mixed order, with a frame asked for twice and jumps forward and back across the start of a clip, each have the mark they have in order.
3. Two renders of one project print the same mark for every frame.
4. The comparison names the first frame, in the order asked, whose mark differs from its mark in order, with both marks. The tests hold this comparison to a control that is made to depend on drawing order on purpose: a renderer that carries one value from the frame it drew before into the next. The control must fail, naming that frame, or the proof proves nothing. A composition cannot be made to depend on drawing order through the notation, which has no state; the control is therefore made at the renderer, the one place a frame drawn before could leak into the next.

The composition of the proof is the fixture `frame-order`: tweens, sets, eased motion, a text that moves, and clips that start and end within its length. No command offers a single frame (section 1): the commands are `check` and `render`, and `render` has no option that names a frame.

## 9. The checked-in pictures

The pictures that define the correct output of this version are checked in under `fixtures/` as PNG files of 8 bits and four channels, one folder for each fixture composition: `fixtures/<name>/composition.xml` and `fixtures/<name>/expected/frame-NNNN.png`, with `NNNN` the frame's number in four digits. The test draws the frames that have a picture on the processor and compares them with the pictures to the byte, pixel by pixel; a pixel that differs fails the test and the message names the frame's number and the first pixel that differs, with both values. A picture is made from the fixture with the example `crates/render/examples/write_expected_pictures.rs` and is read before it is checked in. The test reads the fixtures from `fixtures/`, or from the folder the environment variable `FRAMESMITH_FIXTURES` names, so that a check can show that a picture which is not the checked-in one fails the test. The example `crates/render/examples/read_back_film.rs` (development only) decodes a written film with frx7 and puts chosen frames on one labelled sheet, with the checked-in pictures under them, for the evidence of a ticket. When a frame asked for has no checked-in picture, the example names that frame and the file it looked for, writes no sheet, and exits with 1.

## 10. The log

The lines of a `render` are in `run-log.md` section 4. They hold counts, names of stages and codes, never the project's content, its paths or the words of a report.

## 11. Where the code lives

- `notation` reads the tree of the file (the elements in document order, with their attributes and lines) and the value forms a drawing part reads (a length, a colour).
- `project` holds the project's tree, and the lines of the render settings the project file wrote.
- `layout` places a box: its rectangle in its parent's rectangle (the frame, for a box of the root) from the written `left`, `top`, `right`, `bottom`, `width` and `height` (section 4.1).
- `draw` holds the list of drawing steps and the trait both renderers implement; `draw-cpu` is the renderer on the processor and `draw-gpu` the renderer on the card (`card-renderer.md`), which the command starts for `--backend gpu`, and for `--backend auto` to see whether a card is there (section 1.2).
- `mix` makes the sound of the film (section 5.2): its rate, its channels, its length, and the sounds placed in it (`sound.md`).
- `timeline` makes the scene from a project (and refuses what is not drawn) and draws any frame of it on request (`timeline.md`); `render` takes that scene and writes the film through frx7. The timeline names the footage a frame shows (which source, which picture, at which size) and asks for its pictures through the trait `timeline::Footage`; `render` gives them, decoded, converted and sized through frx7 (`render/src/footage.rs`, section 4.8), so that no system interface enters the timeline. For the forms of a box's place, size, margin and position, `timeline` also gives `check` its reports (`place_reports`, `check-command.md` section 3b), so the two commands judge them by one code.
- `project` also judges the value of each option (`Options`) and takes the settings by the rule of section 1.1 (`Project::apply`, `Settings::source`).
- `cli` is the command: it reads the arguments (the path and the words of the options), calls `project` and `render`, prints, and sets the exit code.
